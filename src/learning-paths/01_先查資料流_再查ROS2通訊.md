# 實戰導讀 01｜ROS 2「收不到資料」怎麼一步步查

> 這是一篇要你能**判斷原因**的課，不是 ROS 2 指令清單。以官方 Demo 的 Publisher／Processor 資料流為主。命令以 ROS 2 Jazzy／Linux shell 說明；目前未在真正 ROS 2 Runtime 驗證。

## 先畫出你以為會發生的事

Publisher 產生數值 → 封裝成 ROS Message → 發佈到 Topic → DDS/RMW 傳送 → Processor 的 Subscription 收到 → Callback 執行 → Processor 產生結果。

如果結果沒有出現，你現在只知道「最後沒看到」，**不知道哪個箭頭沒發生**。不要第一步就更改 QoS、開更多執行緒、或修改算法；那可能讓線索變更少。

## 第一關：程式到底在跑嗎

把錯誤分成兩類：`ros2: command not found` 是環境問題，不能解釋成 ROS 2 通訊失敗；可以執行 `ros2` 但 `ros2 node list` 沒有目標 Node，則可能是程式根本沒啟動、在其他 Domain、發現機制或網路有問題。

在容器內先確認：

```bash
printenv ROS_DISTRO
printenv ROS_DOMAIN_ID
ros2 node list
```

要用到新 terminal 的時候，每個 shell 都要確認自己讀入 ROS 環境。`ROS_DOMAIN_ID` 未設定不等於一定錯，但兩個 Node 必須在相容的 Domain／發現條件下；不能盲目套某個網路教學的設定到考場。

## 第二關：Topic 名字是不是同一個

ROS 2 的 `number`、`/number` 可能在不同 namespace 下成為不同的完整名稱。先看實際圖：

```bash
ros2 topic list -t
ros2 node info /實際的node名稱
ros2 topic info /實際的topic名稱 -v
```

`/實際的topic名稱` 是**佔位符**，請換成 `topic list` 看到的名稱。Topic 被列出來只能證明有這個 ROS Graph 名稱，不代表你的 Subscriber 正在接收正確資料。

## 第三關：Type、QoS 和 Callback 要分開

1. Type 不相同：先修 Type，改 QoS 不能讓不相容的 Message Type 變一致。
2. Type 相同、Endpoint 可見，但沒資料：看 Reliability／Durability 等 QoS 相容性。
3. CLI echo 能看到訊息、應用程式卻沒結果：先檢查 Callback 是否執行、是否因同步等待／阻塞運算被卡住，然後才考慮性能。

`ros2 topic echo` 本身會再開一個訂閱者，因此它能收到不能直接證明應用程式的 Callback 正確。

## 第四關：不要用 MultiThreadedExecutor 遮掩設計問題

假設 Timer Callback 在**同一個 Mutually Exclusive Callback Group** 裡同步等 Service 回覆；即使你把 Executor 換成多執行緒，完成回呼仍可能被這個 Group 擋住。要畫出 Timer → Service call → Future completion 的順序，弄清楚在等誰。可以改用真正非阻塞的 `call_async` 完成回呼，或把需要並行的工作正確分組，但都必須考慮共享資料。

## 你可以自己回答嗎？

**題目 A：** `ros2 topic list -t` 看見 `/number`，可是 Processor 用 `/robot1/number`。先改哪裡？

**題目 B：** 同名、同 Type、Subscriber 仍收不到資料，下一步要看什麼？

**題目 C：** CLI echo 看得見，但 Processor 的 Callback 一直沒有完成。為什麼不該只加大 Queue Depth？

答案：A 先對上完整 Topic 名稱及 Namespace／Remap；B 看兩端 QoS 相容性及實際發佈；C 問題可能在 Callback 執行或阻塞，Depth 只能影響排隊，不會解決邏輯死鎖。
