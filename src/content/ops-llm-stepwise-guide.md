# 統一的操作方式

你把考題、可貼的程式與錯誤交給考場提供的 LLM。它先判斷題目可能屬於哪個技術領域，再每次給一個查詢步驟。**LLM 看不到你沒貼的 Toolkit 頁面**；不知道的 API、檔案和測試結果必須要求確認。

## 開場 Prompt（複製整段）

```text
你是我的程式除錯與效能改善引導助手。
我可以自己打開 NCKU Exam Toolkit 查文章，但你不能假裝已讀過網站。
先讀題目和我提供的原始碼，確認正確性與限制。
每次只給下一個需要查的技術：
【Toolkit 搜尋詞】、【為什麼查】、【讀完要懂什麼】。
不要一次列出一大串方向；若資訊不足先問缺哪一段原始碼。
等我說「查完」再往下。進入修改前先說要改哪個函式、預期改善哪個指標、會影響哪種行為。
每次只修改一個可驗證的假設；給我具體修改與測試指令。
如果正確性下降，先撤回修改。沒有實測數據，不可聲稱一定會加速。
```

## 查完之後

```text
查完了。請用一個很小的例子確認我理解的重點，
然後告訴我下一個要查的 Toolkit 搜尋詞；如果已足夠，改成指出最小修改位置與測試方法。
```

## 看不懂時

```text
我看不懂這一段。請先用 Python 或普通的資料流例子解釋；
只講這個觀念，不要跳到程式修改。我會再告訴你有沒有懂。
```

## 正式改動前

```text
現在請列出你準備修改的檔案、函式、原本行為、改後行為、風險與驗證指令。
如果原始碼或 header 不夠，先告訴我缺哪一段，不能自行補出不存在的 API。
```

## 提問長度有限

先給錯誤、函式簽名與相關 30～100 行，若仍不足再分批貼。純文字剪貼程式時要保留縮排、型別、include 與錯誤訊息。

參考：[GitLab code workflow](https://docs.gitlab.com/topics/git/)、[Git reference](https://git-scm.com/docs)。

## 延伸推演｜遇到變形題怎麼判斷

## 要 AI 幫忙，可以先把問題縮成一個可驗證的改動

不要只寫「幫我優化到最快」。更有效的做法是提供目前檔案路徑、錯誤重現指令、預期結果和你已經確認的限制。例如「這個 pthread 程式兩個 worker 預期計數 40,000，實際偶爾少；只能修同步，不能減少計數工作；先指出 Data Race，再給最小 diff」。

讀 AI 生成的修法時，要分別核對**前提**與**副作用**。如果它想為了速度直接移除日誌，你得先確認那些日誌是否影響外部檢查；如果它建議 `volatile` 解決 Thread 安全，這是錯的，需用 Mutex 或正確的原子同步。若它聲稱某個檔案「已測通過」，你應要求實際測試命令、輸出和退出碼，不能把文字敘述當實測。

**練習：** AI 給了一段 `memcpy(dst, src, n)`，但 `n` 在你的程式代表元素數、每個元素 4 bytes。你要先確認 `dst` 容量和單位，不要因為程式碼看起來更短就照貼。
